# Права доступа

Единый источник правил доступа для всех сервисов и шагов. Код проверяет права так, как описано здесь;
при изменении правил сначала меняется этот документ.

## Роли

Роль определяет права в системе. Должность (справочник `position`) — кадровый признак для оклада и с ролью не связана.
У пользователя может быть несколько ролей, но хотя бы одна. Права складываются: достаточно одной подходящей роли.

| Роль | Кто это | Зона ответственности |
|---|---|---|
| `ADMIN` | Директор, администратор | Админ-панель: учётные записи, сотрудники, зарплаты, финансы; полный доступ ко всему остальному |
| `VET` | Ветеринар | Медицина, медицинское состояние животных |
| `CURATOR` | Куратор | Животные, клетки, фото, склад |
| `ADOPTION_MANAGER` | Менеджер по пристройству | Визиты, заявки, пристройство, фото, мероприятия |
| `COORDINATOR` | Координатор волонтёров | Волонтёры, закрепления, мероприятия |
| `VISITOR` | Посетитель | Публичный каталог и свои заявки |

Посетитель получает роль `VISITOR` при самостоятельной регистрации и не может выбрать другую.
Сотрудников и их роли заводит администратор.

## Где проверяются права

1. **Шлюз** (`gateway-service`) проверяет JWT. Без токена открыты только `/auth/register`, `/auth/login`
   и `/public/**`. Пути `/admin/**` пропускаются только с ролью `ADMIN`. Шлюз удаляет присланные клиентом
   заголовки `X-User-*` и передаёт сервисам подписанные: `X-User-Id`, `X-User-Email`, `X-User-Roles`, `X-Gateway-Signature`.
2. **gateway-auth-starter** в каждом сервисе проверяет подпись, превращает роли в `ROLE_<роль>` и ещё раз
   закрывает `/admin/**` для всех, кроме `ADMIN`. Нет заголовков — 401, подпись не сходится — 403.
3. **Контроллеры** — `@PreAuthorize` по этой матрице. **Сервисы** — правила, зависящие от данных
   (какой статус может поставить роль).

Ошибки доступа — в общем формате `{timestamp, status, error, message, path}`:
401 «Требуется авторизация», 403 «Недостаточно прав для этого действия».

## Этапы жизненного цикла животного

| Код | Название | Клетка | В каталоге |
|---|---|---|---|
| `IN_SHELTER` | в приюте (адаптация, ещё не готов) | обязательна | нет |
| `AVAILABLE` | готов к пристройству | обязательна | да, если не на карантине |
| `RESERVED` | забронирован | обязательна | да, с пометкой «забронирован» |
| `FOSTER` | на передержке | нет | нет |
| `ADOPTED`, `DIED`, `ESCAPED`, `TRANSFERRED` | итоговые (выбыло) | нет | нет |

Допустимые переходы (не итоговые — `PUT /animals/{id}/status`):

| Из | В | Кто |
|---|---|---|
| `IN_SHELTER` | `AVAILABLE`, `FOSTER` | ADMIN, CURATOR |
| `AVAILABLE` | `IN_SHELTER`, `FOSTER` | ADMIN, CURATOR |
| `AVAILABLE` | `RESERVED` | ADMIN (шаг 7 — через заявки) |
| `RESERVED` | `AVAILABLE` | ADMIN (шаг 7 — через заявки) |
| `FOSTER` | `IN_SHELTER`, `AVAILABLE` (с указанием клетки) | ADMIN, CURATOR |

Итоговые статусы ставятся только оформлением выбытия (`POST /animals/{id}/departure`): из любого не итогового,
«пристроен» — только из «готов к пристройству» или «забронирован». Из итогового статуса выйти нельзя
(возврат пристроенного животного — шаг 7). Животное на карантине нельзя сделать готовым к пристройству.

## Связь пользователя и сотрудника

Карточка сотрудника (`shelter_schema.employee`) связана с учётной записью через `user_id`. Администратор создаёт
сотрудника и учётную запись одним действием (`POST /admin/employees`, шаг 6.2) или привязывает существующую учётную запись с ролями сотрудника (`PUT /admin/employees/{id}/account`); роль `VISITOR` сотруднику не назначается. Действия, которые записывают `employee_id`
(процедуры, расход, списание, организация мероприятий), без связанной карточки работающего сотрудника
возвращают 409 «Ваша учётная запись не связана с карточкой сотрудника. Обратитесь к администратору».

**Увольнение и блокировка.** При увольнении (`POST /admin/employees/{id}/termination`) shelter-core-service блокирует
учётную запись в auth-service; при отмене увольнения — разблокирует. Если auth-service недоступен, дата увольнения
не сохраняется (503). Уволенный сотрудник не может войти, а действия, записывающие `employee_id`, для него возвращают 409.
Администратор не может уволить самого себя (409) — так в системе остаётся хотя бы один администратор.

**Ограничение: уже выданный токен уволенного.** Блокировка запрещает новый вход, но JWT, выданный до увольнения,
остаётся действительным до истечения срока — не дольше 8 часов (`JWT_EXPIRATION=28800000`, одна рабочая смена):
отзыва токенов в системе нет, шлюз проверяет только подпись и срок. В это время уволенный может читать то, что
разрешают его роли (списки животных, склад и т. п.); изменения, которые записывают `employee_id` (процедуры, расход,
списание, поставки, мероприятия), отклоняются с 409, потому что карточка уволена. Чтобы закрыть доступ сразу, нужно
отзывать токены (список отозванных в шлюзе или короткий срок жизни с обновлением) — это не реализовано. Срок 8 часов
выбран как компромисс: сотрудник входит один раз за смену, а окно доступа после увольнения втрое меньше прежних 24 часов.

**Внутренний API `/internal/users`.** shelter-core-service вызывает auth-service через OpenFeign: создание учётной
записи (`POST /internal/users`, идемпотентно по `requestId`), чтение (`GET /internal/users/{id}`), блокировка
и разблокировка (`PUT /internal/users/{id}/status`), компенсирующее удаление только той записи, которая создана
этим `requestId` (`DELETE /internal/users/{id}?requestId=`). Шлюз пути `/internal/**` не маршрутизирует (404),
поэтому снаружи они недоступны. Кроме того, auth-service принимает `/internal/**` только с заголовком
`X-Internal-Token`, значение которого совпадает с переменной окружения `INTERNAL_API_TOKEN` (общий секрет
auth-service и shelter-core-service; задаётся в `.env`, пример — `.env.example`). Нет заголовка или значение неверное —
401 «Требуется внутренний токен сервиса (X-Internal-Token)»; подписанные заголовки шлюза, даже с ролью `ADMIN`, его
не заменяют. Без `INTERNAL_API_TOKEN` сервисы не запускаются. Feign-клиент shelter-core-service добавляет заголовок
к каждому вызову; если auth-service отвечает 401 (разные значения у сервисов), shelter-core-service возвращает 503
с подсказкой проверить `INTERNAL_API_TOKEN`. Так внутренний API защищён и при запуске сервисов из IDE, когда порт
auth-service (8180) доступен на локальной машине.

**Idempotency-Key.** `POST /admin/employees` требует заголовок `Idempotency-Key` (UUID; нет или неверный формат — 400).
Повтор с тем же ключом и теми же данными возвращает ту же карточку (200), тот же ключ с другими данными — 409.
